Sparkplug B i Projekt A

Vores ESP32-C6 sender sine målinger som Sparkplug B-beskeder over MQTT. Beskederne går krypteret med TLS via mobilmodemet M5Stack Stamp CatM (SIMCom SIM7080G, LTE-M/NB-IoT) til vores egen cloud-server. Sparkplug B dækker kravet om device-id, timestamp og aflæste værdier. Formatet giver også små payloads, så dataforbruget holdes nede.

Status: forslag. I dag bruger vi almindelige MQTT-topics og JSON. Navne på målinger og ID'er er eksempler og skal tilpasses de sensorer, vi ender med.

Forløb fra opstart til drift

  1. Dataopsamlingen på serveren forbinder og publicerer STATE med "online": true.
  2. ESP32-C6'en tænder Stamp CatM, kommer på mobilnettet og opretter en TLS-forbindelse til mægleren på port 8883.
  3. Ved forbindelsen registrerer ESP32-C6'en sin NDEATH som "Last Will".
  4. ESP32-C6'en sender NBIRTH med alle målinger og et tællernummer, bdSeq. Har den en Modbus-sensor, sender den også DBIRTH.
  5. Derefter måler den med fast interval og sender NDATA. Hver besked har et løbenummer, seq, fra 0 til 255.
  6. Mangler et løbenummer, sender serveren NCMD Node Control/Rebirth, og ESP32-C6'en sender sine birth-beskeder igen.
  7. Mister ESP32-C6'en forbindelsen, sender mægleren dens NDEATH, og serveren markerer data som forældede.

Payloads

Sparkplug B-payloads sendes som Protobuf, altså binært, ikke som JSON. Eksemplerne herunder viser indholdet som JSON, så det kan læses. Kun STATE-beskeden er rigtig JSON.

NBIRTH: skal altid indeholde bdSeq og Node Control/Rebirth. Derefter følger alle målinger med fulde navne og et kort alias.

{
  "timestamp": 1792570000000,
  "seq": 0,
  "metrics": [
    { "name": "bdSeq",                   "datatype": "UInt64",  "value": 0 },
    { "name": "Node Control/Rebirth",    "datatype": "Boolean", "value": false },
    { "name": "Process/Temperature",     "alias": 1, "datatype": "Float",  "value": 22.8 },
    { "name": "Status/CellularRSSI",     "alias": 2, "datatype": "Int32",  "value": -85 },
    { "name": "Status/SupplyVoltage",    "alias": 3, "datatype": "Float",  "value": 3.29 },
    { "name": "Config/SampleInterval_s", "alias": 4, "datatype": "UInt16", "value": 10 }
  ]
}

NDATA med samlede målinger: tre temperaturmålinger med 10 sekunders mellemrum sendes i én besked. Hver måling har sit eget tidsstempel og bruger alias i stedet for navn.

{
  "timestamp": 1792570030000,
  "seq": 1,
  "metrics": [
    { "alias": 1, "timestamp": 1792570010000, "value": 22.9 },
    { "alias": 1, "timestamp": 1792570020000, "value": 23.0 },
    { "alias": 1, "timestamp": 1792570030000, "value": 23.1 },
    { "alias": 2, "timestamp": 1792570030000, "value": -84 }
  ]
}

NCMD fra serveren: ændrer måleintervallet til 15 sekunder uden ny firmware.

{
  "timestamp": 1792570100000,
  "metrics": [ { "name": "Config/SampleInterval_s", "datatype": "UInt16", "value": 15 } ]
}

STATE fra serveren (JSON, sendes med "retain", så klienter, der forbinder senere, ser den med det samme):

{ "online": true, "timestamp": 1792569990000 }

Mobilmodemet: M5Stack Stamp CatM

Stamp CatM er bygget på SIMCom SIM7080G, som understøtter LTE-M og NB-IoT. Begge er mobilteknologier lavet til IoT-enheder med lavt strøm- og dataforbrug. ESP32-C6'en styrer modemet via UART med AT-kommandoer.

Zephyr-driverHvordan den virkerPasser til os?
Generisk mobildriver (CONFIG_MODEM_CELLULAR)Modemet giver ESP32-C6'en en almindelig netværksforbindelse (PPP). Zephyrs egen netværksstak og TLS (mbedTLS) kører på ESP32-C6'en.Ja. TLS og certifikater styres af vores egen firmware.
Særlig SIM7080-driver (CONFIG_MODEM_SIM7080)Modemet håndterer selv forbindelserne (socket offload). Driveren har også GPS.Nej. Driveren understøtter ikke TLS.

Begge drivere bruger devicetree-typen simcom,sim7080 og kræver en GPIO til at tænde modemet (mdm-power-gpios). APN'et til SIM-kortet sættes med CONFIG_MODEM_CELLULAR_APN. Det har vi tjekket i en Zephyr 3.7-kodebase. Vi skal bekræfte, at det er det samme i Zephyr 4.4.

Lavt dataforbrug

TiltagHvordan
Små payloadsProtobuf er binært og fylder mindre end tilsvarende JSON
Alias i stedet for navneNavnene sendes kun i NBIRTH. NDATA bruger korte tal-alias.
Kun ændringerSparkplug sender kun målinger, der har ændret sig ("report by exception"). En lille ændring kan regnes som "ingen ændring".
Samling af målinger (batching)Der måles hvert 5.–15. sekund, men flere målinger sendes samlet i én NDATA, hver med sit eget tidsstempel
Få genforbindelserHver ny TLS-forbindelse koster ekstra data. Forbindelsen holdes derfor åben, eller TLS-sessionen genbruges.

Vi bør måle det faktiske forbrug i bytes pr. time med og uden disse tiltag, og tage tallene med i rapporten.

Lavt strømforbrug, og konflikten med Sparkplug

Sparkplug forventer en vedvarende MQTT-forbindelse, mens lavt strømforbrug kræver, at modem og CPU sover mest muligt. Det skal vi løse bevidst:

  • CPU: ESP32-C6'en sover mellem målingerne og vækkes af en timer eller et interrupt.
  • Modem: SIM7080G understøtter LTE-M's strømsparetilstande PSM og eDRX. Modemet sover, men forbliver registreret på nettet, så det ikke skal logge på igen. Den generiske Zephyr-driver slår dem ikke til, så vi skal selv sende AT-kommandoerne (fx AT+CPSMS). Operatøren skal også understøtte dem på vores SIM-kort.
  • MQTT keep-alive: sættes længere end tiden mellem afsendelser, så mægleren ikke sender NDEATH, mens enheden sover.
  • Hvis forbindelsen alligevel lukkes: sender ESP32-C6'en selv en NDEATH før den sover og en ny NBIRTH når den vågner. Det koster ekstra data, så det skal kun ske sjældent.

Næste skridt

  1. Rette Mosquitto-konfigurationen og slå TLS til på serveren med vores CA.
  2. Forbind Stamp CatM til ESP32-C6'en (UART og en GPIO til at tænde modemet), og få den på LTE-M med den generiske mobildriver. Test først med almindelig MQTT og derefter med TLS.
  3. Skifte til Sparkplug B-beskeder med nanopb, og sætte dataopsamlingen op til at afkode dem.
  4. Indføre batching og søvn, og måle data- og strømforbrug før og efter.
  5. Koble en Modbus-sensor på via HW-519 som device bag ESP32-C6'en.
